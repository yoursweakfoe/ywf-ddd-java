# 批量操作 · 设计卡

## 什么时候需要批量写

后台多选一键处理时用，比如批量确认、批量取消、批量导入。它的本质是同一用例内对**同一聚合的多实例**重复四拍链，四拍链条款见法卷 WC-2。

只有一条需求就用常规写链，不必上批量。批量形态的收益是**编排收敛**：一个 Command，一处声明式事务边界。它不是 SQL 合并。框架逐条循环，每条都走完整领域校验。

## 三个设计决策点

1. **原子性选哪档**：三档。强一致：全批一个事务。部分成功：逐条自治，逐条收集结果。无保证：通知类场景。选择表随形状在册，见法卷 §2.4。判据只有一条：业务能否容忍半途状态。
2. **谁管批大小**：调用方管，框架不管。框架写死上限，等于让容量策略渗进技术骨架；论证在 `MybatisPersistence` javadoc 的「消费契约」节，条款见法卷 BW-5。你的聚合行宽和事务预算自己算。
3. **要不要新层新接口**：不要。批量只是 Command 携带集合的常规形态，法卷 BW-1 禁止为此发明新层。

## 边界与代价

- 批量 = 单事务逐条循环，耗时与连接占用线性于批大小。分片义务就是从这里来的。
- 跨聚合的批量协作不属本模式，走跨聚合卷 `cross-aggregate.md` 法卷。
- 设计原理纵深 → [../explanation/application.md](../explanation/application.md)
