## 什么时候需要批量写

后台多选一键处理（确认、取消、导入）——同一用例内对**同一聚合的多实例**重复四拍链（WC-2）。单条需求用常规写链即可，批量形态的收益是**编排收敛**（一个 Command、一个事务声明式边界），不是 SQL 合并——框架逐条循环、每条走完整领域校验。

## 三个设计决策点

1. **原子性档位**：强一致（全批一事务）/ 部分成功（逐条自治收集）/ 无保证（通知类）——选择表随形状在册（法卷 §2.4）。判据：业务能否容忍半途状态。
2. **谁管批大小**：结论是**调用方管**——框架写死上限等于让容量策略渗入技术骨架（论证见 `MybatisPersistence` javadoc「消费契约」节，法卷 BW-5）。你的聚合行宽与事务预算自己算。
3. **要不要新层新接口**：不要——批量只是 Command 携带集合的常规形态（法卷 BW-1 禁发明新层）。

## 边界与代价

- 批量=单事务逐条循环，耗时与连接占用线性于批大小（这就是分片义务的来源）
- 跨聚合的批量协作不属于本模式（走跨聚合卷 `cross-aggregate.md` 法卷）
- 设计原理纵深 → [../explanation/application.md](../explanation/application.md)
