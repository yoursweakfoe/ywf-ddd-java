# 安全层解读（身份与验签为什么长这样）

> 本页回答"这套框架的安全层为什么长成这样"：凭据由谁验、为什么要验、验完看见什么、验签能力自己怎么演化。条款与代码形状 → [common-security 法卷](../../specs/current/modules/security.md)；API 与配置事实 → [common-security 字典](../reference/api/common-security.md)。本页属地图区宽松件：与法卷冲突以法卷为准（宽严双份，法卷赢）；这里只承载法条背后的"为什么"。

## 一句话总图

门口有网关守路由，每个服务自验凭据；验完的凭据原样可读、不做投影；验签的密钥方案可插拔可分发。四件事共用同一个底层判断：**网络里的身份声明一律不可信，可信只来自当场验签。**

## 边界分工：谁守门，谁守身

鉴权被切成两层，各归其位。**路由级**——"这个路径允不允许外部访问"——是南北向入口的策略，交给网关（Higress，充当 PEP 策略执行点）；**细粒度**——"当前这个人对这个操作有没有资格"——只有服务自己懂自己的业务，下沉到服务的方法级声明。

理解了这条分工，才不会觉得服务侧那条默认放行的安全链是裸奔：它的职责本来就**不是拦客，是认人**——把每一个带凭据的请求验签、建立起身份；放不放行某条路由，红线在网关画。同时这条链被刻意做成**可被业务覆盖**：框架不焊死任何安全策略，服务对自己的防御纵深负全责，框架只提供默认姿态与替换接缝。

## 为什么服务要自己验凭据

第一代实现不是这样：曾经由网关验签、服务信任网关透传的身份 Header（旧 ADR-0014 时代）——这条路的死因值得留一句诚实的话：Header 可以在内网被伪造，"信任上一跳"的隐含前提与"不信任网络、每跳验证"的零信任原则直接冲突，故整套模型被 ADR-0018 废止，配套的身份来源标记与预认证过滤器一并作古（空号判例，无正文）。

现行裁决把因果倒了过来：**网关降格为转发者**，它转发原始 JWT，不再做任何身份断言；**每个服务下沉为 OAuth2 资源服务器**，用可插拔的验签能力当场自证凭据真伪。身份的可信度从此与"请求经过了谁"无关，只与"签名对不对"有关。

配套的两条硬姿态都是同一哲学的延伸：

- **fail-closed**：坏 token 一律 401 拒之门外，绝不吞异常静默放行——旧框架"验不过就算了"的吞异常做法是反面教材，身份层宁可拒绝也不装没事。
- **签发与验签分家**：服务侧不提供签发、刷新、登出能力，那些归独立认证服务（IdP）。服务是凭据的消费者，既当运动员又当裁判的形态一次都不出现。

零信任对东西向（服务间调用）同样成立：透传原始凭据、下游再自验一遍——这个主题的原理归云侧解读承载（快照账 ADR-0026），本页只指出它是同一原则换个方向而已。

## 验完之后看见什么：身份即凭据，不投影

真实的 JWT 世界是混乱的：字段命名无规范、数量不定——有的凭据只有用户号，有的带用户名，有的还带部门分部。若框架替所有人投影一个固定形状的身份结构，别人多一个字段、少一个字段，投影就失配——等于**把别人家的混乱焊进自己的契约**，每次上游字段变化都逼框架改版。

裁决是彻底不猜：**principal 保持原生凭据结构**（它本身就是一张全量声明的映射表），框架只提供"按名字自取"的读取机制，缺哪个字段就读出空值，不炸不猜。命名责任归业务——业务读自己凭据里的字段，天经地义；框架管机制——验签、建身份、读声明，与具体字段无关。

唯一的例外是一处刻意留出的"字段缝"：鉴权机制需要一个公认的"角色 → 权限"换算，而角色字段叫什么名各家不同，于是框架把这个**唯一必须由约定对齐的字段名留成配置位**。除此之外不写死任何字段名。这不是妥协收尾，是"机制与字段分离"的边界标本：能抽象全抽象，抽象不掉的才暴露为配置。

## 验签能力本身：可插拔、按算法分发

签名算法世界同样是多元的：不同来源的凭据用不同密钥方案（对称的、非对称的），且短期内不会统一。单一固定验签方案等于框架替全公司选密钥——不现实。

裁决：**验签是一个抽象接口，实现按凭据自带的算法声明分发**——来一个 token，看它自己声明用什么签的，路由到对应实现。由此获得三条性质：新增签名方案 = 新增一个实现，框架抽象不改一分（对扩展开放）；未知算法直接拒绝（fail-closed 语义在分发层的复读）；框架保持薄——分发器是可选工具，谁需要谁装配，框架不强塞。

这个抽象还是一个**留着的逃生舱**：对称密钥意味着"能验签者皆能签发"，任一服务被攻破即可伪造 token，这是当前形态明知要还的债；长远迁非对称（公钥验签、私钥只在签发方）时，只需往分发接口里换一个实现，验签侧各服务零改动。

## 不做的边界（同样是设计）

以下刻意**不**归安全层管，且不是疏忽：RBAC 的权限模型、行级数据过滤——与业务模型强耦合，焊进框架只会造出一个谁都要绕开的抽象；机器身份（定时任务、MQ 这类没有用户上下文的调用）——需凭据体系另开口子，现行叙事不覆盖；长链透传同一凭据的受众限制与令牌交换——演进项，抽象已就绪，按需再立。划清"不管什么"与建好"怎么管"同等重要：安全层的每个接缝都指向"机制在框架、策略在外部"这条同一主线。

**决策快照账**（以下判例正文冻结于卷宗区，只供溯源、永久不回改；本段是现行论证，随法演化）：

- ADR-0014（决策快照）—— 网关验签 + 服务信任 Header 模型，已被 ADR-0018 取代；本页仅存一句历史交代。
- ADR-0016（决策快照）—— 边界 permit-all 安全链：路由级归网关、细粒度归服务、链可覆盖。
- ADR-0018（决策快照）—— 零信任：服务自验 JWT，网关降为 PEP 只转发凭据，fail-closed。
- ADR-0019（决策快照）—— 身份不投影：原生凭据按名字自取，角色字段名是唯一配置缝。
- ADR-0020（决策快照）—— 验签可插拔：验签抽象 + 按算法分发，未知算法拒绝，不强制装配。
