# 云集成 — 框架为什么这样跟云上生态咬合

> 本页回答「这套框架为什么这样接 Spring Cloud / 阿里云生态」：东西向怎么调、熔断交给谁、Nacos 与 Seata 怎么引进来、身份怎么沿调用链走。依赖坐标、配置键、代码形状的唯一权威在法卷——[common-cloud 模块卷](../../specs/current/modules/cloud.md)、[分布式事务卷](../../specs/current/patterns/distributed-tx.md)、[security 模块卷](../../specs/current/modules/security.md)、[外部集成卷](../../specs/current/patterns/external-gateway.md)；本页只是这些形状背后的为什么（宽松件，与法卷冲突以法卷为准）。未采纳模式的账目在 [theory-map 微服务治理节](theory-map.md)。

## 贯穿六案的一条气质：用生态，不入教派

把云集成层的几桩决定摆在一起，看到的是同一个提问方式：每次要引入一个生态组件，问的从来不是「装哪套全家桶」，而是「我此刻缺哪一块能力」。于是有了这些看似矛盾其实同源的取舍——收了 SCA 的 starter，却拒收同属 SCA 的 Sentinel；收了注册发现的自动装配，却甩掉 BOM 的版本绑架；用 Seata 做分布式事务，却拒绝把它的透传形态焊进框架；同样是跨服务透传一个 header，JWT 内置、XID 不内置。**组件逐个点名、版本节奏自持、框架保持薄、模式稳不稳决定焊不焊**——下面按主题展开。

## 东西向传输：为什么是朴素的 HTTP

gRPC 曾摆上桌面，但强类型协议的收益有前提：接口量大、调用频密、性能确实卡在序列化上。本框架的内部接口量少，这个前提不成立；而且强类型契约已经由 contract jar 用另一种方式提供了——消费方直接依赖同一份 Java 接口与 CQE/CO，契约不兼容在编译期就显形，protobuf 想解决的问题已被前置消化。更实的一层是复用：对外经 Higress 暴露的本来就是 REST 端点（Controller 即契约接口的实现），东西向复用同一组端点，鉴权、异常映射、文档都不用立第二套机制；协议收敛为一种，适配代码显著收窄——当时账面上记过节省规模，那是会议数字，今天的理由是「一套契约、一套安全模型」这个形状本身。

落地形态：一期 RestClient 静态地址直连，Feign 作声明式客户端经 common-cloud opt-in，Nacos 服务发现留作二期开关——不注册也能调，注册只是把地址来源换掉。形状细则在 cloud 模块卷与分布式事务卷，此处不复制。

## 韧性：只要熔断，不背一个流量治理平台

引入 SCA 之后桌上有过两个熔断选项。裁决靠的是职责盘点而非功能对比：入口限流已经归 Higress 网关，监控告警已由 common-observability 承担——落到客户端的需求只剩「被我调用的那一位挂了，我要快速失败加降级」这一条。Sentinel 的不可替代能力（系统自适应保护、热点参数限流、集群流控、Dashboard）全部面向大流量治理场景，恰好都落在已被网关接管的边界之外；接受它等于为一块用不到的平台背下资源定义、双套 fallback 处理器和整套部署配置。Resilience4j 正好是剩下那个洞的形状：轻量容错库、一套 fallback 收口、可纯配置驱动零注解，且经 Spring Cloud 的 CircuitBreaker 抽象使用，日后要换不连坐业务代码。

还有一条长期成立的判据：依赖选型要看上游的长期健康——当时一边近乎停更、对新 Boot 大版本靠补丁续命，另一边随 Spring Cloud 同步发布。具体版本快照会过期，「生态组件必须跟得上主版本节奏」这个标准不过期。放弃项照账：热点流控一类能力确没有了，但需要它们的场景本就不在客户端这一层。

## 注册与配置中心：收 starter，不收版本绑架

需要 Nacos 的注册发现与配置中心能力时，裸 nacos-client 只是编程式 SDK——DiscoveryClient、配置注入全要自写。SCA starter 的自动装配价值（LoadBalancer 自动从 Nacos 取实例、`spring.config.import` 声明式拉配置）明显压过多接受一个构件的成本，于是收；但 starter 的便利连着 BOM 的版本绑架——SCA 的发布节奏落后于 Nacos 官方，照单全收等于把升级时钟交给别人。解法立了此后反复复用的一般规则：**构件经 starter 收编、版本由框架父工程 dependencyManagement 独立覆盖**——用谁的新版自己定。边界同样清楚：SCA 止步 discovery + config 两个构件，不顺带 Sentinel 等其余家当（上一章的熔断拒收正是这条边界的另一半）。

一期东西向仍是静态直连，Nacos 属二期预留——这条决定回答的是「将来引入时按什么姿势接」，姿势已经立好。

## 分布式事务：Seata 拿来用，不焊进来

Seata 的引入复刻了上面的版本自主权：独立构件、版本独立管理，升级不受任何生态 BOM 发布节奏约束。更有味道的是透传侧的裁决：分布式事务成链要求 XID 跨服务透传，框架却拒绝内置这个能力——**模式未稳，框架不焊死**。header 定名、出站拦截器与入站 Filter 的挂点、上下文绑定的清理时机，这些还没收敛成一种公认形态；焊进框架等于让全体消费方共担认知修正的成本，而框架定位本就偏薄。于是框架只提供事务构件与开关，透传以配方模板沉淀——双端各手写一环，缺环即断链，这条铁律的现行法在 [分布式事务卷](../../specs/current/patterns/distributed-tx.md)。

对照下一章的 JWT 透传「内置」：同样是往 HTTP header 里放东西，去向相反，尺子却唯一——**稳了就焊，没稳就配方**。这也是「XID 不进框架」当年真正的论证：不是透传本身不好，是它的形状还没长死。

## 身份传播：零信任沿调用链延伸

安全侧早有定案：每个服务都是资源服务器、自验 JWT、不信任网络本身。东西向调用是这条原则的延伸场景，也是最容易被悄悄破功的场景——「网关验签后注入身份 Header、下游直接信 Header」在内网网段里不成立：Header 在网络内可伪造，信任 Header 就是退回网络信任。mTLS / SPIFFE 能在传输层解决，但背后站着证书体系或服务网格——与本项目的规模不匹配，且网格在治理层已被否过一次。

JWT 透传是零额外基础设施的一条路：出站拦截器从当前线程 SecurityContext 取已验签的 Jwt，原样挂上 `Authorization: Bearer`；下游按 common-security 自验。同一份凭据贯穿全链，用户身份跨服务连续可审计，没有任何一个服务需要「信任另一个服务」——验的是签名，不是来路。它内置于 common-cloud（Feign 栈的 RequestInterceptor，缺依赖静默不激活），因为模式在当时已经稳：这是与 XID「不内置」互为镜像的裁决，判据即上一章那句尺子。

两处已知缝隙，是账不是秘密：机器身份（定时任务、MQ 消费没有用户上下文）需另行走 client-credentials 取 token，框架未代办；长链一路透传同一枚 token，受众与 scope 的收窄尚未落地——深链上最小权限做到哪一层，留待后案裁决。
