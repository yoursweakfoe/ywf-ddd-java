# 可观测性的薄法（日志止于 stdout，追踪交给 Agent）

> 本页回答"这套框架的可观测性为什么止步于此"：日志只打到 stdout、追踪只在部署时挂载、收集与告警一概不住应用侧。能力清单、配置形状与依赖构成是事实，住 [common-observability 字典](../reference/api/common-observability.md)；用法承诺以 [observability 法卷](../../specs/current/modules/observability.md) 为准——本页与法卷冲突时法卷赢（宽严双份），本页只讲它背后的为什么。

## 日志的归宿：它是事件流，不是文件

应用对日志的想象应当停在"把事件按序说出口"这一刻。本框架的部署目标是容器平台，实例天生短命：弹性扩缩让"哪个实例写了哪个文件"无从追溯，落盘的日志随实例销毁而蒸发，散落各节点的文件既无人轮转也无人清理——文件落盘把平台的分内事（统一收集、集中存储）抢回了应用侧，换来的只有运维复杂度。所以日志只走 stdout，由平台侧采集器统一接管：应用输出结构化事件，采集、汇聚、检索全在平台，两侧各守其界。

推论是同一条边界落在库与应用之间：框架库不携带日志输出配置。配置权归最终应用——一个库替它下面所有应用决定日志去向，是本末倒置；结构化日志是应用侧一行开关的事（形状见字典 §2，此处不抄），框架要做的只是让 Spring Boot 的内置能力开箱可及。

## 薄的另一半：追踪是部署形态，不是构建依赖

链路追踪曾在"引入 SDK 依赖"与"部署时挂载 Agent"之间做过取舍，最终选了后者，理由至今成立：**零代码侵入**——业务代码与构建产物里没有半个追踪 SDK 的类型，埋点、上下文传播全部发生在字节码之外；**未挂载时零副作用**——不挂 Agent 的进程 classpath 干净、MDC 里没有 trace 键，日志照常输出，应用不因追踪缺席而坏掉分毫。

于是追踪能力随部署形态出现或消失，而非随代码版本变化：同一份构建产物，挂上 Agent 即可对接任意追踪后端（那是一个运维环境变量，不是一次代码变更），摘下即回到无追踪状态。追踪基础设施的选型更迭——换后端、换供应商——永远不必敲开工程的门。代价也在这里：**构建与测试看不见追踪能力**，Agent 是否挂对只能在运行期观察；框架接受这笔账，因为让代码干净地躺进任何环境的价值高于把一切能力钉死在依赖清单里。

## 同一条裁线：应用只管产出，不管承接

日志、指标、追踪三件事共享同一刀切法：应用只负责产出材料——结构化事件流（日志）、数值端点（指标）、可被采集的上下文（trace 关联）；至于材料之后的去向与用途——告警规则、仪表盘、慢查询分析——一概住平台侧，不进应用 SDK 的职责（边界细目见字典 §7，不复述）。可观测性做"薄"不是能力缺失，而是把每一分职责放给生命周期与它匹配的一侧：会随平台演化的不住代码里，随业务演化的才住代码里。
