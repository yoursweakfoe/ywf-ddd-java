# 聚合身份编译期隔离：类型化 ID（Typed Identifier）
- Slug: 2026-09-typed-identifier ｜ 日期: 2026-09-11

## Why（为什么现在改）
现状：聚合 ID 全域裸用底层类型（现为 UUID），各聚合身份在类型系统里同形——把 A 聚合的 ID 传进期待 B 聚合 ID 的调用位（跨聚合编排传参错位、`findAllById` 结果复用进错仓储等），编译器无从察觉，错误迟到运行时才暴露。业界（jMolecules `Identifier`、branded ID 实践）已把「类型化 ID」视为建模词汇层的编译防线。驱动力：本框架经裁决不载事件管线与长流程机制（见「不做」），词汇层的编译防线是框架侧余下收益成本比最优的增量——一次定型、无运行期机制、无 bug 膨胀面。

## What changes（做什么，非怎么做）
- 为聚合作者改：每个聚合铸造专属 ID 终类型（教例 `{Agg}Id`，如 PaymentId），调用位混入他聚合 ID = 编译失败；「拿着 A 的 UUID 调 B 的方法」这类事故从运行时提前到编译期。
- 为外部消费方：HTTP wire 与 OpenAPI 形态零变化（Q1 已裁边界内路线，见 §裁决记录）。
- 为框架：common-ddd 增发纯 Java 身份词汇（现有 `Identifiable`/`AggregateRoot<ID>` 泛型链原样承接，不破坏改造）；`AggregateIds.mint()` 铸造面不受牵动，机制本身不绑定 UUID——底层类型由各聚合自定（Q4 划界）。
- 法卷与工具面：聚合蓝图 domain 槽位、编码公约类型后缀表、ddd 模块卷聚合根场景各挂增量；skills（new-aggregate / new-usecase / batch-operations）模板随动。施工动作住 tasks，本件不复制。

## 验收标准（AC 账 — 人话摘要 + 编号；法条正文住 plan §delta，此处零条文）
- AC-1 混放编译锁：他聚合 ID 传入本聚合 ID 调用位编译必失败；正确放置必通过；非 ID 调用位不受误伤。负证明探针在册（先例参照：TransactionBoundaryProbes 的四锁纪律——新防线不过负证明即空文）。
- AC-2 词汇发行零依赖：domain 层新增身份词汇为纯 Java，零新增运行时依赖，R4 现行域纯度规则原样绿。
- AC-3 wire 零破坏：契约层 CQE/CO 的 JSON 形态与 OpenAPI schema 施工前后逐字节一致（取证：契约面快照对比或既有 schema 测试对账）。
- AC-4 持久化零侵入：PO 形状、`DddMapper` 七条语句、XML SQL 文本、DB schema 四类全零修改；领域 ID → 持久化主键的转换集中于仓储 `toPersistenceId` 一位（每仓储恰一处）。
- AC-5 机制不绑类型：以 Long 承载的教例 ID 按同一套条款成立（编译 + 测试绿）；本 AC 只证词汇面兼容，不含 DB 自增落地。
- AC-6 示例闭环迁移：sample 全部聚合迁至类型化 ID 作参考实现，全量 mvn 绿 + `ddd-review` 内置七闸绿。
- AC-7 折叠日文档齐：delta 起量后 glossary、设计卡同题节、skills 指针随动，check-docs 七闸全绿。

## 约束
- domain 零框架运行时依赖不动（stereotype 豁免面不扩大）。
- 手写 SQL 文本教义不动：PO 保持原生值类型，转换只发生在仓储层一位。
- 既有泛型链 `Identifiable<ID>` / `Entity<ID>` / `AggregateRoot<ID>` / `Repository<Domain, ID>` / `MybatisPersistence<…, ID>` 不做破坏性改造——方案必须原样经由这些槽位进入。
- 契约层现行「聚合 ID 引用一律 UUID」条款群（写链/蓝图/批量/跨聚合/应用对象诸卷）的触改量以 Q1 裁定为限，不预防性放开。
- 两门两停，过 Plan 门方可施工；施工中发现范围溢出回门重批。

## 不做（范围边界）
- 不借本案复活事件管线 / Saga / 长流程——该三方向已有实践裁决（实现面代码膨胀、bug 面失控，场景自持为纲），要入典另案。
- 不做任何聚合的实际换形（现有聚合底层承载保持 UUID、库表零动）——AC-5 仅证机制类型无感。
- 不引入 jMolecules 依赖——借其词汇思路，不引入其制品（框架惯风：只发行角色词汇）。
- 不做跨聚合 `Association` 代理 / 延迟寻址设施——本案只裁身份类型隔离。
- 不触 equals/hashCode、判等教义现行条款。
- 不立 DB 代铸聚合的「创建即合法」例外语义（通道在持久契约已留，首用者另案）。
- 不提供 bigint 发号设施（号段/雪花等铸造入口属接真实自增聚合时的独立小案，本案只裁来源分类合法）。

## 待你裁决的 N 问
- Q1 覆盖面：A=域内路线——类型化 ID 住 domain/application/infrastructure，契约层维持裸 UUID，进 Handler 前一点解析定型（倾向：零 wire 破坏、条款群触改面最小，防错收益全部保留在跨聚合调用位）；B=全域路线——契约与 Controller 签名同用 `{Agg}Id`（收益：对外自述更强；价：ID 类型落位引发分层新边、wire/OpenAPI 兼容工程、五卷条款同改）。
- Q2 词汇形态：A=common-ddd 增发一个纯 Java 身份接口词汇，`{Agg}Id` 为其 record 实现（倾向：ArchUnit 可按类型执法、javadoc 有锚）；B=不发词汇纯命名约定 + ArchUnit 按 `*Id` 名识别（省一个接口，执法面变脆）。
- Q3 解析位（仅当 Q1=A）：A=Handler/读端口实现入口显式一点 `of(...)` 定型（倾向：单点、可 grep、可测）；B=框架/自动转换代劳（与无拦截器教义相抵，倾向拒）。
- Q4 自增承载划界：A=本案只保「机制不绑底层类型」，DB 代铸身份的「创建即合法」例外语义等真实自增聚合出现时另案（倾向：不为尚未存在的需求立法）；B=本案一并补 DB 代铸语义。
